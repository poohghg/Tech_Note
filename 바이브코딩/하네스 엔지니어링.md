> **하네스란 AI 에이전트가 안전하고 예측 가능한 방식으로 작동하도록 환경을 설계하는 기술이다.**
> 
> 프롬프트를 통한 에이전트 제어는 한계가 있다. 에이전트는 프롬프트를 무시할 수 있기 때문이다. 따라서 하네스는 반드시 시스템 제약을 통해 에이전트의 행동을 강제해야 한다. 구현시 세세하게 지시하지 말되 반드시 지켜야 할 규칙은 기계적으로 강제해야 한다. 하네스 엔지니어링에서 중요한건 에이전트가 올바른 방향으로 작동하도록 제약을 걸고, 에이전트의 결과물을 검증할 수 있는 장치를 마련하는 것이다. 즉 ==에이전트가 올바르게 일하는 환경을 구축하는== 것이다. 
 
1. 잘못된 실행방식을 억제한다. -> 제약을 걸수록 에이전트 생산성이 올라간다.
2. AI는 자기 결과물을 스스로 제대로 평가 못 함(저품질의 생산성) -> 에이전트가 자기 작업을 외부 기준으로 검증 할 수 있는 장치가 필요 

예를 들어 다음과 같은 장치가 필요하다.
- 자동테스트: 코드 -> 즉시 검증
- 타입 체크 & 린터 -> 규칙 위반 -> 즉각 피드백
- 검증 다각화: 코드 작성 모델 -> 검증 모델

또한 
- 정리 전담 에이전트를 주기적으로 가동
- 문서-코드 일치 검사 에이전트
- 아키텍처 규칙 위반 탐지 에이전트등을 실행한다.

### 하네스의 구성

| 구성 요소   | 역할                | 예시                       |     |
| ------- | ----------------- | ------------------------ | --- |
| 지시 문서   | 에이전트에게 규칙을 전달     | `AGENTS.md`, `CLAUDE.md` |     |
| 아키텍처 제약 | 구조적으로 잘못된 코드를 차단  | 린터, 디렉토리 규칙              |     |
| 피드백 루프  | 에이전트 행동을 실시간으로 교정 | 테스트, CI 자동화              |     |

##### 에이전트 와 하네스

> 에이전트는 사용자에게 보이는 행동이다. 목표를 이해하고 도구를 쓰고 결과를 고치고, 사람에게 보고하는 전체 행동 패턴이다.

> 하네스는 에이전트의 행동이 나아도록 모델 주변에 설치된 기계장치다. 오케스트레이션 루프, 도구, 도구 실행기, 메모리, 컨텍스트 압축, 권한 정책, 오류 처리 , 검증 루프가 여기에 속한다.
### 하네스의 역할

> 하네스는 단순히 AI에이전트를 동작시키는 구조가 아니라, AI 에이전트의 생산성을 극대화하고, 안전하게 운영되도록 하는 역할을 한다.

- 제어: 에이전트가 허용된 범위 밖의 행동을 하지 않도록 제한하는 구조
- 감시: 에이전트의 동작 상태와 출력 결과를 실시간으로 추적,기록
- 개선: 오류나 이상 동작을 감지하고 다음 동작에 반영하는 피드백 루프
### 핵심 원칙

1. 결과물이 안 좋을 때 같은 모델이라도 하네스 설계에 따라 결과물이 달라진다.
	1. 하네스 설계에 따라 결과물의 품질이 달라진다.
	2. 모델 변경 방식보다는 하네스 설계 변경 방식이 더 효과적이다.
2. 완벽한 시스템을 미리 설계하려 하지 말고, 점진적으로 개선하라.
	1. 에이전트 실행 -> 실패 시 구조적 방지 장치 추가
3. 적게 넣어라.
	1. 하네스는 최소한의 규칙으로 최대한의 효과를 내야 한다.
	2. 규칙을 너무 많이 넣으면 오히려 성능 저하가 발생 할 수 있다.
	3. 규칙파일은 결국 성능 저하 + 토큰 낭비를 초래한다.
4. 말로만 하지 말고, 반드시 검증 가능한 장치를 만들어라.
	1. 프롬프트는 에이전트가 무시 할 수있다.
	2. 반면 시스템 제약은 에이전트가 무시할 수 없다.
	3. 규칙을 만들면 반드시 검증 장치를 만들어라.
	4. 검증 장치가 없다면 규칙은 의미가 없다.	
	5. 예를 들어
	    1. 코드 작성 규칙 -> 린터
	    2. 테스트 작성 규칙 -> 자동 테스트
	    3. 문서 작성 규칙 -> 문서-코드 일치 검사 에이전트
5. 하네스도 진화한다.
	1. 하네스 설계도 점진적으로 개선되어야 한다.
	2. 모델과 함께 하네스 설계도 개선되어야 한다.
