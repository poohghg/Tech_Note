> 프롬프트: "좋은 코드를 짜줘라고 말함"
> 하네스: 좋은 코드를 기계적으로 강제
> 
> 구현방식은 세세하게 지시하지 말되 반드시 지켜야 할 규칙은 기계적으로 강제해라.
> 
> 잘못된 실행방식을 억제한다. -> 제약을 걸수록 에이전트 생산성이 올라감.
> AI는 자기 결과물을 스스로 제대로 평가 못 함(저품질의 생산성) -> 에이전트가 자기 작업을 외부 기준으로 검증 할 수 있는 장치가 필요 
> 
> 예를들어
> 자동테스트: 코드 -> 즉시 검증
> 타입 체크 & 린터 -> 규칙 위반 -> 즉각 피드백
> 검증 다각화: 코즈 작성 모델 -> 검증 모델
> 
> 정리 전담 에이전트를 주기적으로 가동한다.
> 문서-코드 일치 검사 에이전트
> 아키텍처 규칙 위반 탐지 에이전트

### 핵심 원칙

1. 결과물이 안 좋을 때 같은 모델이라도 하네스 설계에 따라 결과물이 달라진다.
	1. 하네스 설계에 따라 결과물의 품질이 달라진다.
	2. 모델 변경 방식보다는 하네스 설계 변경 방식이 더 효과적이다.
2. 완벽한 시스템을 미리 설계하려 하지 말고, 점진적으로 개선하라.
	1. 에이전트 실행 -> 실패 시 구조적 방지 장치 추가
3. 적게 넣어라.
	1. 하네스는 최소한의 규칙으로 최대한의 효과를 내야 한다.
	2. 규칙을 너무 많이 넣으면 오히려 성능 저하가 발생 할 수 있다.
	3. 규칙파일은 결국 성능 저하 + 토큰 낭비를 초래한다.
4. 말로만 하지 말고, 반드시 검증 가능한 장치를 만들어라.
	1. 프롬프트는 에이전
	2. 규칙을 만들면 반드시 검증 장치를 만들어라.
	3. 검증 장치가 없다면 규칙은 의미가 없다.
