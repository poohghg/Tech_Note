### 1.HTML 웹 페이지 요청하기
---
> 웹 서버는 브라우저에 보내듣 HTTP 응답 헤더의 Content-Type필드를 통해 지금 응답하는 데이터가 어떤 타입의 데이터인지 브라우저에게 알려준다.

- Content-Type: text/html 이고 UTF-8로 인코딩된 파일이므로 HTML파일로 다뤄서 DOM파싱을 해야하는 데이터이고, 데이터의 바이트를 UTF-8로 디코딩해야 한다는 것을 브라우저에게 알려준다.
- Content-Encoding: br, gzip, deflate 등으로 압축되어 있는 경우에는 브라우저가 압축을 해제해야 한다는 것을 알려준다.
	- br: Brotli 압축 알고리즘으로 압축되어 있다는 것을 알려준다.
	- gzip: Gzip 압축 알고리즘으로 압축되어 있다는 것을 알려준다.
	- deflate: Deflate 압축 알고리즘으로 압축되어 있다는 것을 알려준다.

> 웹 서버가 응답 헤더를 통해 브라우저에 서버와 현재 전송하는 데이터에 대한 정보를 전달하는 것처럼 브라우저도 요청 헤더를 통해 서버에 브라우저와 현재 전송하는 데이터에 대한 정보를 전달한다.

> #### HTML 요청 순서

1. DNS 리졸브와 HTTPS 보안 연결까지 맺어지고 나면 브라우저는 웹 서버에 HTML 파일을 요청한다.
2. 브라우저는 웹 서버에 요청을 보내 때, HTTP 요청 헤더를 사용하여 현재의 요청과 브라우저에 대한 정보를 서버에 보내고, 웹 서버는 HTTP 응답 헤더를 사용하여 전달받은 데이터가 어떤 타입의 데이터인지 브라우저에게 알려준다.
3. 브라우저는 응답 헤더의 Content-Type필드를 확인하여 HTML 파일로 다뤄야 하는지, JSON 파일로 다뤄야 하는지, 이미지 파일로 다뤄야 하는지 등을 확인한다.
4. HTTP헤더는 HTTP 프로토콜을 사용하여 오가는 데이터에 대한 정보와 요청자, 수신자에 대한 정보를 포함한다. 웹 서비스를 효율적으로 개발하도록 돕는 Next.js 등 프레임워크에서도 HTTP 헤더를 사용하여 리소스를 브라우저 맞게 최적화한다.

### 2.HTML 파싱 및 DOM 트리 구축
---
> 브라우저는 DOM(Document Object Model) 트리를 구축하기 위해 HTML 파일을 파싱한다. 

![[Pasted image 20260726180346.png]]

> DOM은 Document Object Model의 약자로, HTML 문서를 객체 모델로 표현한 것이다. DOM은 HTML 문서의 구조를 트리 형태로 나타내며, 각 HTML 요소는 노드(node)로 표현된다. 이를 통해 브라우저는 HTML 문서를 이해하고, 자바스크립트와 상호작용할 수 있게 된다.

> HTML이 웹 페이지가 어떻게 구조화되는지를 정적으로 표현한다면 DOM은 브라우저에서 이 HTML파일을 해석해서 ==화면에 렌더링하려고 사용하는 동적인 객체 모델==이다. 즉, HTML은 정적인 문서이고 DOM은 동적인 객체 모델이다.

> 브라우저는 웹 서버에서 받은 HTML 스트링을 문법 규칙에 맞게 파싱한 후 div,body 등의 요소를 노드라는 이름의 객체로 만들어 메모리에 저장한다.
> 
> 각 노드에는 div,span 처럼 HTML 요소를 식별하는 tagName과 스타일 정보를 비롯한 속성 정보를 저장하는 attributes, 자식 노드와 부모 노드의 관계를 나타내는 childNodes, parentNode 등의 속성이 존재한다. 이러한 노드들을 연결하여 트리 구조로 만들어진 것이 바로 DOM 트리이다. 이 전체 트리는 메모리에 저장되어 스크립트를 통해 DOM API의 형태로 접근된다. 


> HTML 파싱 중 script 태그를 만나면 브라우저는 HTML 파싱을 일시 중단하고, 스크립트 파일을 다운로드하고 실행한 후 다시 HTML 파싱을 이어간다. 이는 스크립트가 DOM에 접근하여 조작할 수 있기 때문이다. 따라서 스크립트가 DOM을 조작하기 전에 DOM이 완전히 구축되도록 하기 위해, 일반적으로 script 태그는 body 태그의 마지막에 위치시키거나, defer 또는 async 속성을 사용하여 비동기적으로 로드하는 것이 권장된다.

#### DOMContentLoaded 이벤트 와 load 이벤트

> 브라우저는 HTML 파싱을 마치고 ==DOM트리를 구축하고 나면 DOMContentLoaded 이벤트==를 발생시킨다. 이 이벤트는 HTML 문서가 완전히 로드되고 DOM 트리가 구축되었음을 나타낸다. 따라서 이 이벤트를 통해 자바스크립트는 DOM 요소에 접근하고 조작할 수 있다.

> Load 이벤트는 ==DOM트리 구축뿐 아니라 이 DOM트리가 화면에 각각의 노드들이 참조하는 여러 외부 리소스(이미지, 스타일시트, 스크립트 등)==까지 모두 로드되었을 때 발생한다. 따라서 load 이벤트는 DOMContentLoaded 이벤트보다 늦게 발생하며, 모든 리소스가 준비된 후에 실행되어야 하는 코드에 적합하다.

#### HTML 파싱 요약

1. 브라우저는 HTML 파일을 파싱해서 DOM이라는 객체 모델을 구축한다.
2. HTML은 웹 페이지의 정적 표현이고, DOM은 웹 페이지를 동적으로 변경하게 해주는 객체 모델이다.
3. 브라우저는 HTML 각 요소를 노드라는 형태의 객체로 메모리에 저장한다. 이 노드에는 문서 노드, 요소 노드, 텍스트 노드, 속성 노드 등 다양한 종류가 존재하며, tagName, attributes, childNodes, parentNode 등의 속성을 가진다.
4. HTML을 파싱하는 HTML파서는 다른 프로그래밍 언어의 파서와는 다르게 문맥 에 따라 유연하게 파싱한다. 예를 들어, HTML 문서에서 닫는 태그가 생략된 경우에도 HTML파서는 이를 보완하여 DOM트리를 구축한다.
5. HTML 파싱이 마무리되어 DOM트리가 구축되면 브라우저는 DOMContentLoaded 이벤트를 발생시킨다. 이 이벤트는 HTML 문서가 완전히 로드되고 DOM 트리가 구축되었음을 나타낸다.

### 3. CSS 파싱 및 CSSOM 트리 구축
---
> DOM은 HTML문서의 각요소가 가진 계층 구조를 표현하는 모델로, 각 요소가 어떤 크기와 어떤 색깔로, 어디에 그려야 할지 등의 스타일 정보를 알지 못한다. 따라서 브라우저는 CSS 파일을 파싱하여 CSSOM(CSS Object Model)이라는 객체 모델을 구축한다.

> CSSOM 트리는 각 요소에 적용될 스타일이 어떤 구조로 이루어지는지를 나타낸다. 브라우저는 DOM 트리와 CSSOM 트리를 결합하여 렌더 트리를 구축한다. 렌더 트리는 각 요소가 화면에 어떻게 표시될지를 결정하는데 필요한 정보를 포함하고 있다.

### 4.렌더 트리 구성
---
> ==렌더 트리는 실제로 화면에 나타나야 하는 요소들의 계층 구조를 표현한 것으로 DOM트리나 HTML 문서와 완벽하게 1:1로 대응되지 않는다.== 렌더 트리는 DOM트리와 CSSOM트리를 결합하여 브라우저가 화면에 표시할 요소들의 구조와 스타일 정보를 포함하는 객체 모델이다. 렌더 트리는 실제로 화면에 표시될 요소들만 포함하며, display: none 속성이 적용된 요소들은 렌더 트리에 포함되지 않는다. 브라우저는 렌더 트리의 요소들을 기반으로 레이아웃을 계산하고 페인트 단계를 거쳐 화면에 웹페이지를 렌더링한다.

> HTML, CSS 파싱과 마찬가지로 렌더링엔진의 의해 일어난다.
> 크롬에서는 블랭크라는 렌더링 엔진에 의해 이 과정이 수행되며, ==렌더러 프로세스의 메인 스레드==에서 동작하므로 HTML 파싱과 CSS파싱에 의존적으로 수행된다.

#### 렌터트리와 HTML의 관계

![[Pasted image 20260728180611.png]]


> 렌더 트리는 HTML과 CSS를 바탕으로 화면에 무엇이 그려져야 할지를 표현한다는 점에서 DOM요소와 부합해야 하지만 DOM트리의 요소와 렌더 트리의 요소가 1:1로 대응되지 않는다. 이는 CSS의 여러 속성 때문이다.

- `<head>` 태그처럼 화면에 렌더링되지 않는 비시가적 DOM 요소는 DOM트리에는 존재하지만 렌더 트리에는 나타나지 않는다.
- display: none 속성이 적용된 요소는 DOM트리에는 존재하지만 렌더 트리에는 나타나지 않는다.
- 한 줄에 충분히 표시할 수 없는 문자가 여러 줄로 바뀔 때 새 줄은 별도의 렌더 객체로 추가 되는 경우가 있다.
- DOM 노드에 대응하지만 트리의 동일한 위치에 있지 않을 수 있다. 예를 들어 float 처리된 요소나 position 속성이 적용된 요소는 렌더 트리에서 다른 위치에 나타날 수 있다.

### 5. 레이아웃 계산
---
> 렌더 트리가 구축되면 브라우저는 ==각 요소의 정확한 위치와 크기를 계산하는 레이아웃(layout) 단계를 수행한다. 이 과정에서 브라우저는 렌더 트리의 각 노드에 대해 화면 좌표를 계산하고, 부모 요소와 자식 요소 간의 관계를 고려하여 요소들이 화면에 어떻게 배치될지를 결정한다.==

> 레이아웃은 화면에 그려져야 할 모든 요소의 정보가 있는 렌더 트리에서 시작하므로 최상단에 위치하는 루트 노드부터 재귀적으로 진행된다. 루트노드는(0,0)좌표를 가지며 루트 노드의 크기는 사용자 화면에 나타나는 브라우저 원도우의 크기, 즉 뷰포트 (viewport) 크기와 동일하다. 루트노드의 자식 노드들은 루트노드의 좌표를 기준으로 상대적인 위치를 가지며, 각 자식 노드의 크기는 CSS 속성에 따라 결정된다. 이러한 과정을 반복하여 모든 요소의 위치와 크기를 계산한다.

> DOM이 업데이트되어 위 계산 과정을 DOM의 일부 혹은 전체에 대해 다시 반복하는 경우, 이를 ==Reflow==라고 한다. Reflow는 브라우저의 성능에 큰 영향을 미치므로, DOM 조작 시에는 Reflow를 최소화하는 것이 중요하다. 예를 들어, 여러 DOM 요소를 한 번에 변경하는 대신, DocumentFragment를 사용하여 변경 후 한 번에 DOM에 추가하는 방식이 권장된다.

> 페이지를 렌더링하는 과정에서 연산시간의 많은 부분을 차지하는 레이아웃 계산은 브라우저의 성능에 큰 영향을 미치므로, 개발자는 레이아웃 계산을 최소화하도록 코드를 작성하는 것이 중요하다. 예를 들어, CSS 속성 중에서 레이아웃 계산을 유발하는 속성을 최소화하고, DOM 조작 시에는 Reflow를 최소화하는 방식으로 코드를 작성하는 것이 좋다.

#### 요소의 크기를 결정하는 기준, 박스 모델

> 레이아웃 계산 과정에서 브라우저가 렌더 요소의 크기를 결정할 때 기준으로 삼는 것은 CSS의 박스 모델에 기반한 바운딩 박스이다.

![[Pasted image 20260728181815.png]]

> 브라우저에서 화면에 그려지는 모든 요소는 박스로 표현된다.
> 실제로 화면에 그려지는 요소의 모양이 사각형이 아니라도 브라우저는 모든 요소를 박스 모델에 기반한 스타일이 적용된 박스로 인식하고 이들을 조합하여 화면을 구상하고 요소들을 배치한다.

![[Pasted image 20260728181947.png|342]]

- content: 요소의 실제 내용이 표시되는 영역으로, 텍스트, 이미지 등 콘텐츠가 위치한다.
	- width와 height 속성은 content 영역의 크기를 지정한다.
	- box-sizing 속성에 따라 content 영역의 크기를 계산하는 방식이 달라진다.
		- box-sizing: content-box (기본값): width와 height는 content 영역의 크기를 지정한다. padding과 border는 content 영역의 크기에 포함되지 않는다.
		- box-sizing: border-box: width와 height는 content, padding, border를 모두 포함한 크기를 지정한다. 따라서 padding과 border가 추가되더라도 요소의 전체 크기는 변하지 않는다
		- 예를 들어 200px의 width를 가진 요소에 20px의 padding과 5px의 border가 적용되면, content-box에서는 요소의 전체 크기가 250px(200 + 20 + 20 + 5 + 5)이 되지만, border-box에서는 요소의 전체 크기가 여전히 200px로 유지되며 실제 내부 넓이는 155px(200 - 20 - 20 - 5 - 5)가 된다.
- 패딩: 콘텐츠와 보더 사이의 영역이다. 콘텐츠에 대한 내부 여백 역할을 하며, 콘텐츠는 영역을 더 크게 만들어 준다. 콘텐츠 영역에서 적용되는 배경 색상이나 배경 이미지는 이 패딩 영역까지 확장되어 적용된다.
- 보더: 요소의 테두리를 나타내는 영역으로, 패딩과 마찬가지로 요소의 크기를 증가시키는 역할을 한다. 보더는 요소의 외부 경계를 정의하며, 스타일, 색상, 두께 등을 지정할 수 있다.
- 마진: 요소와 다른 요소 사이의 외부 여백을 나타내는 영역으로, 요소의 크기를 증가시키지 않는다. 마진은 요소 간의 간격을 조절하는 데 사용되며, 요소의 배경색이나 배경 이미지는 마진 영역에는 적용되지 않는다.

> 박스 모델의 각 영역은 요소의 최종 크기와 위치를 결정하는데 중요한 역할을 한다.
> 브라우저는 레이아웃 계산 과정을 통해 HTML 요소마다 바운딩 박스를 적용하고 CSS를 통해 바운딩 박스의 스타일을 설정한다. 그 후 이를 기반으로 부모 요소와 인접한 다른 요소들을 고려해 바운딩 박스가 실제 뷰포트의 어느 좌표에 어떻게 그려질지를 계산한다.

#### 요약

1. 렌더 트리가 구성되고 나면 렌더 트리의 각 요소가 사용자의 뷰포트에 어떻게 그야져야 할 지 계산하는 작업이 필요하다. 이를 레이아웃 계산 과정이라고 한다.
2. 레이아웃 계사은 복잡한 작업이다. 각 요소의 바운딩 박스를 구하고 이들이 실제로 그려질 좌표와 크기를 구해야한다. 레이아웃 과정은 전체 브라우저 렌더링 사이클에서 가장 많은 연산을 소모하는 과정이다. 따라서 개발자는 레이아웃 계산을 최소화하도록 코드를 작성하는 것이 중요하다.
3. 브라우저가 레이아웃 과정에서 각 요소를 계산할 때 기본으로 잡는 단위는 박스이다. 브라우저는 각 요소를 박스를 기준으로 컨텐츠, 패딩, 보더, 마진이 들어 있는 박스 모델로 바라보며, CSS도 이 박스 모델을 기준으로 요소에 스타일을 적용한다.
4. CSS의 속성들은 이 박스 모델의 각요소가 어떻게 보일지를 결정한다.

### 6.페인트
---
> 어떤 요소들을 어떤 순서대로 쌓아 올려야 하는지를 결정한 후에 각 요소를 주어진 스타일에 맞게 칠하는 작업을 수행하는게 페인트 고정이다

> 레이아웃 계산이 끝나면 브라우저는 각 요소의 위치와 크기를 기반으로 화면에 실제로 그려지는 페인트(paint) 단계를 수행한다. 이 과정에서 브라우저는 렌더 트리의 각 노드에 대해 색상, 배경, 텍스트, 그림자 등 시각적인 스타일을 적용하여 픽셀 단위로 화면에 렌더링한다.

> 브라우저는 각 요소를 3차원의 레이어로 구성하므로 한 요소가 다른 요소보다 위에 쌓여야 하는지 아래에 쌓여야 하는지 등 공간 정보를 계산하여 최종적으로 화면에 표시될 순서를 결정한다. 이 과정에서 z-index 속성이나 position 속성 등이 중요한 역할을 한다.

#### Stacking Context(쌓임 맥락)

> 쌓임 맥락은 가상의 z축을 사용한 HTML 요소의 3차원 개념화이다.
> Z축은 사용자 기준이며 사용자는 뷰포트 혹은 웹 페이지를 바라본다고 가정한다.
> 각 HTML 요소는 자신의 속성에 따른 우선순위를 사용해 3차원 공간을 차지한다.

![[Pasted image 20260802144224.png|534]]

> 쌓임 맥락은 독릭적이며 계층 구조를 지닌다.
> 자식 요소들은 부모 요소의 쌓임 맥락 내에서만 의미가 있다. 만약 어떤 요소를 화면의 제일 위쪽으로 가져오려고 z-index를 높이더라도 의도한 대로 동작하지 않는다면 그것은 해당 요소의 부모의 쌓임 맥락이 다른 요소의 쌓임 맥락보다 아래에 있기 때문이다. 따라서 부모 요소의 쌓임 맥락을 고려하여 자식 요소의 z-index를 설정해야 한다.

##### 쌓임 맥락을 생성하는 조건
- position 속성이 absolute, relative, fixed, sticky인 요소 
- opacity 속성의 값이 1보다 작은 요소
- transform, filter, perspective, clip-path, mask, mask-image, mask-border 속성의 값이 none이 아닌 요소
- mix-blend-mode 속성의 값이 normal이 아닌 요소
- isolation 속성의 값이 isolate인 요소
- z-index 속성의 값이 auto가 아닌 요소
- flex 컨테이너의 자식 요소(z-index 값이 auto가 아닌 경우)
- grid 컨테이너의 자식 요소(z-index 값이 auto가 아닌 경우)
- contain 속성의 값이 layout, paint 또는 composite인 요소
- will-change 속성의 값이 stacking-related property를 포함하는 요소
- 모바일 브라우저에서 position: fixed 또는 position: sticky 속성을 가진 요소

#### 페인트 요약

1. 페인트 과정은 단순히 요소들을 칠하는 과정뿐 아니라, 위치와 크기가 정해진 각 요소가 어떤 순서대로 화면에 그려져야 하는지, ==어떤 요소가 어떤 요소 위에 그려져야 하는지 등 우선순위==를 결정하는 과정도 포함한다.
2. 브라우저는 페인트 과정에서 한 요소가 어떤 요소보다 위에 쌓여야 하는지 아래에 쌓여야 하는지 등 공간 정보를 계산하여 최종적으로 화면에 표시될 순서를 결정한다. 이 과정에서 z-index 속성이나 position 속성 등이 중요한 역할을 한다.
3. 요소의 페인트 우선순위를 결정하고 나면 브라우저는 CSS를 바탕으로 요소를 스타일링한다. 이 과정이 끝나고 나면 비로소 브라우저는 어떤 요소들을 어떤 크기로, 어떤 위치에, 어떤 순서로, 어떤 스타일을 적용해서 그려야 할지 알게 된다.

### 7.픽셀화&컴포지션
---
> 사용자에게 보이는 것은 GPU를 통해 화면에 그려지는 픽셀이다.
> 
> 페인트 과정에서 브라우저는 각 요소를 스타일링하여 화면에 그릴 준비를 마친다. 그러나 실제로 화면에 표시되기 위해서는 각 요소를 픽셀 단위로 변환하고, 여러 레이어를 결합하여 최종 이미지를 생성하는 컴포지션(composition) 단계가 필요하다.
> 
> 브라우저는 앞선 단계들을 거치면 얻은 정보를 바탕으로 각 픽셀이 어떻게 표시되어야 할지를 정한다.
> 이 과정은 크게 픽셀화와 컴포지션을 통해 이루워진다. 위 과정을 거치고 나면 브라우저는 2차원 픽셀 데이터의 배열을 얻는다., 이 배열을 GPU에 전달하여 화면에 렌더링한다.

#### 레이어

> 브라우저에서는 하나의 페이지를 여러 레이어로 나누어 렌더링한다. ==레이어는 브라우저가 화면에 표시할 요소들을 그룹화==한 것으로, 각 레이어는 독립적으로 렌더링될 수 있다. 레이어를 나누는 이유는 성능 최적화와 재렌더링 최소화를 위해서이다.

> 브라우저는 다양한 기준으로 레이어를 나눈다. 예를 들어, position 속성이 fixed인 요소, z-index 속성이 높은 요소, transform 속성이 적용된 요소 등은 별도의 레이어로 분리될 수 있다. 이렇게 나누어진 레이어들은 독립적으로 렌더링(각각의 레이어를 별도로 픽셀화)되며, 필요할 때만 다시 페인트되고 합성된다.

#### 픽셀화

> 픽셀화는 브라우저가 그려야 할 레이어를 실제 화면에 표시하려고 픽셀 단위의 데이터로 변환하는 과정을 의미한다. 브라우저가 여러 과정을 거쳐 뷰포트에 표시할 레이어 들을 생성하면 렌더러 프로세스는 각 레이어의 정보를 활용해 GPU가 이해하는 형태로 픽셀화 과정을 수행한다. 픽셀화 과정이 끝나고 나면 브라우저는 픽셀화된 레이어들을 조합하여 사용자에게 보여줄 화면을 GPU를 통해 보여준다.

> 성능 최적화의 관점에서 브라우저는 필요에 따라 특정 레이어들을 사전에 픽셀화하며 사용자의 스크롤, 애니메이션, 인터랙션 등으로 인해 레이어가 변경될 때마다 전체 페이지를 다시 렌더링하는 것이 아니라, 변경된 레이어만 다시 페인트하고 컴포지션하여 화면에 표시한다. 이를 통해 브라우저는 렌더링 성능을 향상시키고 사용자 경험을 개선한다.

#### 컴포지션

> 컴포지션은 픽셀화된 레이어들을 결합하여 최종 이미지를 생성하는 과정을 의미한다. 브라우저는 각 레이어의 z-index, position, opacity 등의 속성을 고려하여 레이어들을 올바른 순서로 합성하고, 최종적으로 GPU를 통해 화면에 표시한다.
> 
> 브라우저에서 수행하는 컴포지션은 픽셀화된 여러 레이어를 하나의 완성된 프레임으로 결합하는 렌더링의 최종 단계이다.

#### 컴포지션의 단계

1. 레이어의 결정과 분리: 브라우저의 렌더링 엔진은 레이아웃 트리에 정의된 각 요소를 복잡성, 애니메이션 유무, 자주 변경되는 여부 등 을 고려하여 레이어로 분리한다. 예를 들어, position 속성이 fixed인 요소, z-index 속성이 높은 요소, transform 속성이 적용된 요소 등은 별도의 레이어로 분리될 수 있다.
2. 픽셀화: 각 레이어는 GPU가 이해할 수 있는 형태로 픽셀화된다. 이 과정에서 브라우저는 각 레이어의 스타일, 색상, 텍스처 등을 기반으로 픽셀 데이터를 생성한다.
3. 최종 컴포지션: 브라우저 렌더링 엔진은 현재 사용자의 뷰포트에 표시되어야 하는 레이어들을 선택하고 이들을 최종적인 프레임으로 결합한다. 이 과정에서 레이어의 순서, 투명도, 변환 등을 고려하여 화면에 그려낼 최종 스크린 샷을 생성한다. 최종 컴포지션 단계는 매우 중요하다. 이는 브라우저가 레이어들의 일부만이 화면에 표시되기 때문이다.

> 브라우저에서 레이어를 분리하는 기준은 여러 가지이다. 주로 CSS 속성에 의해 분리되는데, 공식 문서에서 안내하는 대표적인 몇 가지 기준을 살펴보면 transform, opacity, filter, animation, will-change 등 특정 요소들에 독립적으로 적용되어야 하는 스타일들이 적용되면 해당 요소는 레이어가 분리되어 별도로 관리되고, 화면에 표시될 때 컴포지션을 통해 결합된다.
