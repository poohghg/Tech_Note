> 브라우저는 초당 60 프레임을 목표로 렌더링을 수행한다. 이는 ==1초에 60번 화면==을 새로 그린다는 의미이며, 각 프레임은 약 16.67ms(1000ms / 60) 동안 처리되어야 합니다. 만약 렌더링이 이 시간을 초과하면, 사용자는 화면이 끊기거나 느리게 반응하는 것을 경험하게 된다.

#### 레이어 분리

> 화면에 렌더링해야 하는 요소들에 변경 사항이 생기더라도 브라우저가 항상 모든 렌더링 단계를 다시 수행하지 않는다. 브라우저는 렌더링 과정에서 레이어를 분리하여, 변경된 부분만 다시 렌더링하도록 최적화한다. 예를 들어, 화면의 일부 요소가 변경되었을 때, 브라우저는 해당 요소가 속한 레이어만 다시 그리게 된다. 이를 통해 불필요한 렌더링 작업을 줄이고 성능을 향상시킬 수 있다.

> 만약 특정 레이어의 스타일이나 위치가 변경되어 레이아웃이나 페인트 단계를 다시 수행하게 되더라도 브라우저는 변경에 영향을 받는 해당 레이어에 필요한 연산만을 다시 수행하면 된다. 따라서 하나의 화면을 자주 변경되는, 혹은 함깨 변경되는 요소들로 묶어 하나의 레이어로 분리하면 렌더링 성능이 개선된다.> 

> 성능 좋은 웹 페이지를 만드려면 화면을 사용자에게 의미 있는 단위로 분리하고, 자주 변경되는 요소들을 하나의 레이어로 묶어 렌더링 효율을 높이는 것이 중요하다.
> 예를 들어 시멘틱하게 관련 있는 요소들을 하나의 레이어로 묶어, 해당 레이어에 변경이 발생했을 때만 다시 렌더링하도록 설계하는 것이 좋다. 이렇게 하면 불필요한 렌더링 작업을 줄이고, 사용자 경험을 향상시킬 수 있다.

브라우저는 기본적으로 페이지를 하나의 거대한 캔버스로 보고 그림(Paint)을 그리지만, 특정 CSS 속성을 만나면 해당 요소를 독립된 레이어로 떼어내어 GPU에게 처리를 맡긴다. 이렇게 하면 애니메이션이나 전환 효과가 발생할 때 페이지 전체를 다시 그리지 않고(Repaint 방지), 미리 그려진 레이어들의 위치만 재조합(Composite)하므로 60fps의 부드러운 성능을 낼 수 있다.

1. `will-change` 속성 (권장): 브라우저에게 "이 요소는 곧 특정 속성이 변경될 거야"라고 미리 힌트를 주는 가장 명확한 방법입니다. 브라우저는 이 힌트를 보고 선제적으로 요소를 독립된 렌더링 레이어로 분리합니다.

``` css
/* CSS */
.modal-window {
  will-change: transform, opacity;
}
```

Tailwind CSS v4를 활용한 UI 컴포넌트 구성 시에는 유틸리티 클래스로 간단히 적용할 수 있습니다.

TypeScript

```
// React / Next.js 환경의 Tailwind 적용 예시
<div className="transform transition-transform will-change-transform hover:scale-105">
  상호작용이 많은 카드 컴포넌트
</div>
```

### B. 3D Transform 강제 적용 (전통적인 방식)

`will-change`가 지원되기 전부터 쓰이던 방식이자, 여전히 유효한 트리거입니다. Z축을 포함한 3D 변형이 일어나면 브라우저는 무조건 해당 요소를 별도 레이어로 승격시킵니다.

CSS

```
.layer-promoted {
  /* 실제 시각적 변화는 없지만 GPU 레이어 생성을 강제함 */
  transform: translateZ(0); 
  /* 또는 */
  transform: translate3d(0, 0, 0);
}
```

### C. 자연스러운 레이어 분리 조건

개발자가 명시하지 않아도 브라우저가 스스로 레이어로 분리하는 요소들도 있습니다.

- `<video>`, `<canvas>`, `<iframe>` 요소
    
- `opacity` 속성에 CSS 애니메이션/트랜지션이 활성화된 경우
    
- `position: fixed` 요소 (특정 조건 만족 시)
    

## 2. 적절한 수준을 찾기 위한 모니터링 방법

레이어가 많아지면 GPU의 VRAM(메모리) 사용량이 급증하고, 분리된 레이어들을 다시 합치는(Composite) 과정에서 병목이 생겨 오히려 성능이 저하됩니다. 크롬 개발자 도구(Chrome DevTools)를 통해 이를 눈으로 확인하며 조율해야 합니다.

### A. 렌더링(Rendering) 탭의 '레이어 테두리' 확인

가장 직관적으로 현재 페이지의 레이어 개수를 확인하는 방법입니다.

1. 크롬 개발자 도구 열기 (`F12` 또는 `Cmd+Option+I`)
    
2. `Esc` 키를 눌러 하단 드로어(Drawer)를 엽니다.
    
3. 좌측 상단 점 3개 메뉴 `⋮` > **More tools** > **Rendering** 선택.
    
4. **Layer borders(레이어 테두리)** 옵션을 체크합니다.
    
5. **결과:** 화면에 주황색/청록색 격자가 생깁니다. 청록색 테두리로 둘러싸인 영역이 각각의 독립된 레이어입니다. 불필요하게 많은 요소에 청록색 테두리가 쳐져 있다면 최적화가 필요합니다.
    

### B. Layers(레이어) 패널 분석

레이어가 생성된 '원인'과 차지하는 '메모리'를 정확히 파악할 수 있습니다.

1. 개발자 도구 우측 상단 톱니바퀴 옆 `⋮` > **More tools** > **Layers** 선택.
    
2. 좌측 트리에 현재 생성된 레이어 목록이 표시되고, 중앙에 페이지의 3D 구조가 나타납니다.
    
3. 특정 레이어를 클릭하면 우측 하단 **Details** 창에 해당 레이어가 생성된 이유(Compositing Reasons)와 메모리 추정치(Memory estimate)가 뜹니다.
    

### C. Performance(성능) 패널 프로파일링

실제 렌더링 프레임 저하가 발생하는지 확인합니다.

1. **Performance** 탭으로 이동.
    
2. 설정(톱니바퀴 아이콘)에서 Enable advanced paint instrumentation(고급 페인트 계측 사용)을 체크.
    
3. 녹화 버튼을 누르고 페이지와 상호작용(스크롤, 모달 띄우기 등)한 뒤 녹화 중지.
    
4. 타임라인에서 **Composite Layers** 이벤트가 너무 많은 시간(보통 1~2ms 이상)을 차지하지 않는지, 불필요한 **Paint**가 발생하지 않았는지 확인합니다.
    

## 3. 적용 시 주의사항 및 최적화 원칙

- **변화가 끝난 후 해제하기:** `will-change`는 메모리를 미리 할당하므로, 애니메이션이 끝난 후에는 속성을 제거하여 브라우저가 메모리를 회수할 수 있게 해주는 것이 좋습니다.
    
- **최상위 컨테이너에 남용 금지:** 페이지 전체를 감싸는 `<main>`이나 `<body>` 등에 레이어 분리를 지시하면 거대한 텍스처가 VRAM에 올라가 기기에 큰 부담을 줍니다. 크기가 작고 빈번하게 움직이는 리스트 아이템이나 모달 팝업, 툴팁 등에만 제한적으로 사용해야 합니다.
    
- **Paint 플래싱 확인:** 앞서 렌더링 탭에서 Paint flashing(페인트 깜박임)을 켜고 상호작용을 해보세요. 녹색 깜박임이 나타나는 곳이 CPU가 다시 그리고 있는 영역입니다. 애니메이션 요소에 녹색 깜박임이 지속해서 발생한다면 레이어 분리가 제대로 안 된 것입니다.
